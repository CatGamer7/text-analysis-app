# Исследование вариантов упаковки бэкенда (Backend Packaging Research)

## 1. Введение и контекст проекта

Проект **text-analysis-app** разрабатывается как настольное (десктопное) оффлайн-приложение для социологов и исследователей. Архитектура приложения состоит из двух ключевых компонентов:
- **Фронтенд:** Десктопная оболочка на **Electron** (React + TypeScript).
- **Бэкенд:** Сервис на **Python (FastAPI)**, обеспечивающий локальный инференс открытых языковых моделей (HuggingFace Transformers / PyTorch / ONNX Runtime).

### Целевая аудитория и ограничения:
1. **Нетехнические пользователи (исследователи):** У пользователя не должны требоваться предустановленный Python, компиляторы C++, драйверы CUDA или ручной запуск консоли. Приложение должно устанавливаться стандартным инсталлятором (`setup.exe` / `.msi` / `.dmg`).
2. **Оффлайн-работа:** Все компоненты, зависимости и базовые веса моделей должны функционировать локально без постоянного интернет-соединения.
3. **Размер дистрибутива:** Стандартная связка `PyTorch + Transformers` «из коробки» занимает от 2 до 4 ГБ. Требуются оптимизации для минимизации размера установщика.
4. **Скорость холодного старта:** Запуск локального сервиса не должен занимать более 2-4 секунд.

## 2. Сравнительный анализ подходов к упаковке

Было проведено исследование пяти основных вариантов упаковки бэкенда:

| Критерий | 1. PyInstaller (`--onedir`) | 2. PyInstaller (`--onefile`) | 3. Embedded Python (портативный) | 4. Nuitka / PyOxidizer | 5. Docker Desktop |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Время холодного старта** | 🟢 **Высокое (1–3 с)** | 🔴 Низкое (15–35 с, распаковка в `%TEMP%`) | 🟢 **Высокое (1–2 с)** | 🟢 Высокое | 🔴 Низкое (запуск VM/демона) |
| **Сложность сборки** | 🟢 **Низкая/Средняя** | 🟢 Низкая | 🟡 Средняя (ручной `.pth` и wheel) | 🔴 Высокая (ошибки линковки torch) | 🟢 Низкая |
| **Интеграция с Electron** | 🟢 **Отличная (Sidecar)** | 🟡 Средняя | 🟢 **Отличная** | 🟡 Средняя | 🔴 Сложная (зависимость от среды) |
| **Требования к ОС клиента** | 🟢 **Стандартные** | 🟢 Стандартные | 🟢 **Стандартные** | 🟢 Стандартные | 🔴 Требует WSL2/Hyper-V/Admin |
| **Размер итоговой папки** | 🟡 150–500 МБ (с ONNX) | 🟡 150–500 МБ (архив) | 🟡 120–400 МБ | 🟢 100–300 МБ | 🔴 Несколько гигабайт |

### Детальный разбор вариантов:

### Вариант 1: PyInstaller в режиме `--onedir` (Каталог файлов) — РЕКОМЕНДУЕМЫЙ
- **Механизм:** Утилита собирает бинарник `backend.exe` и все зависимые DLL, `.pyd` и библиотечные файлы в отдельную директорию `dist/backend/`.
- **Преимущества:**
  - Отсутствие задержки на распаковку архива во временную папку при каждом старте.
  - Легко инспектировать зависимости и исключать неиспользуемые модули (например, `scipy`, `matplotlib`, `tkinter`, `cuda/cublas`, если инференс ведётся на CPU).
  - Electron может запускать `dist/backend/backend.exe` напрямую через `child_process.spawn`.
- **Особенности:** Для корректной сборки FastAPI/Uvicorn требуется явное указание скрытых импортов (`uvicorn.logging`, `uvicorn.loops`, `app.api`).

### Вариант 2: Embedded Python (Python embeddable package)
- **Механизм:** Официальный zip-архив с минимальным Python от python.org (~15 МБ), в который распаковываются зависимости из колес (`wheel`) и настраивается `python3xx._pth`.
- **Преимущества:** Полный контроль над файловой структурой, максимальная прозрачность для обновления скриптов без пересборки бинарника.
- **Недостатки:** Требует написания собственных скриптов подготовки окружения и запуска.

### Вариант 3: Nuitka
- **Механизм:** Трансляция Python-кода в C++ с последующей компиляцией в нативный машинный код.
- **Недостатки для данного проекта:** Огромное время компиляции (30-60+ минут на CI), высокий риск несовместимости со специфическими C-расширениями PyTorch и HuggingFace Tokenizers на Windows.

### Вариант 4: Docker Desktop
- **Вердикт:** Категорически не подходит для конечных пользователей-гуманитариев, так как требует установки Docker, прав администратора, включения виртуализации BIOS и занимает гигабайты дискового пространства.

## 3. Оптимизация размера ML-компонентов: Переход на ONNX Runtime

Ключевая проблема упаковки бэкендов на Python с PyTorch — размер библиотеки `torch` (более 1.5–2.5 ГБ даже для CPU-версии из-за статических библиотек OpenMP, MKL и BLAS).

### Рекомендуемая стратегия:
1. **Экспорт моделей в ONNX:** Модели классификации тональности и токсичности (RuBERT-tiny2, Twitter-RoBERTa) переводятся в формат ONNX через HuggingFace `optimum` или `torch.onnx.export`.
2. **Использование `onnxruntime` вместо `torch`:** Библиотека `onnxruntime` весит всего **~40 МБ** (против ~2 ГБ у PyTorch), при этом инференс на CPU работает в 2–3 раза быстрее благодаря оптимизациям под инструкции AVX2/AVX-512.
3. **Результат:** Суммарный размер упакованного бэкенда сокращается с **~2.8 ГБ до ~180 МБ**.

## 4. Архитектура взаимодействия с Electron (Sidecar Pattern)

Бэкенд запускается фронтендом Electron как дочерний процесс:

```
[ Пользователь ]
       │
       ▼
[ Electron Frontend ] (React UI)
       │
       ├──── 1. Запуск child_process.spawn("backend.exe", ["--port", "8000"])
       ├──── 2. Ожидание готовности: polling GET http://127.0.0.1:8000/api/v1/health
       ├──── 3. Взаимодействие по HTTP/REST (OpenAPI контракты)
       │
       ▼ (при закрытии окна)
[ Electron Main ] ────> 4. Корректная остановка: отправка SIGINT или POST /api/v1/shutdown
```

### Безопасность и отказоустойчивость:
- Привязка сокета только к локальному интерфейсу `127.0.0.1` (без доступа из внешней локальной сети).
- Динамический выбор свободного порта (передаётся через аргумент `--port` или переменную окружения).
- Healthcheck с таймаутом (если бэкенд не ответил за 10 секунд, UI отображает понятный экран ошибки).

## 5. Итоговый план реализации упаковки

1. **Базовый этап (текущий):** Спецификация `packaging/pyinstaller.spec` и автоматический скрипт сборки `packaging/package_backend.py`.
2. **Оптимизация:** Перевод энкодерных моделей на ONNX Runtime для минимизации размера инсталлятора.
3. **CI/CD:** Сборка GitHub Actions на раннере `windows-latest` с выгрузкой артефактов в релизы.
